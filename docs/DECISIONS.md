# تصمیم‌های فنی

## Next.js + NestJS + PostgreSQL

انتخاب شد چون با نمونه‌ی Hotel-Yab هم‌راستا، قابل Deployment روی VPS و برای جداسازی UI بازی از منطق معتبر امتیاز مناسب است. اجرای بازی کاملاً داخل Next.js یا Local Storage ساده‌تر بود، اما رکوردها قابل اعتماد و مشترک بین کاربران نبودند.

## Canvas به‌جای DOM برای Gameplay

Canvas برای ده‌ها حرکت، Particle و Trail در هر ثانیه سربار Layout کمتری دارد و روی Mobile قابل پیش‌بینی‌تر است. UI معمولی، Dialog و Leaderboard همچنان Semantic HTML هستند.

## REST و Modular Monolith

GraphQL، WebSocket و Microservice برای Gameplay فعلی ارزش کافی ندارند. REST برای Start/Finish و دریافت Leaderboard کافی است.

## Schedule قطعی از Seed سرور

سرور می‌تواند بدون اعتماد به Client حضور Targetها را بازسازی کند. ارسال Score خام یا نگهداری کامل Session در Browser رد شد.

## WebP ثابت + CSS برای خرچ/خروچ

نسخه‌های Scale2 ابتدا به‌صورت MP4 و سپس Animated WebP شفاف ارزیابی شدند. MP4 به‌خاطر زمینه‌ی مشکی H.264 و Animated WebP به‌خاطر بازپخش Instanceهای هم‌منبع هنگام اضافه‌شدن افکت تازه کنار گذاشته شد. Runtime به WebPهای ثابت قبلی برگشته است؛ CSS رشد پیوسته از `scale(0)`، ماندگاری و خروج را کنترل می‌کند و «خروچ» ۴۲۰ میلی‌ثانیه بعد از «خرچ» ظاهر می‌شود. Cooldown مشترک ۹۰۰ میلی‌ثانیه‌ای مانع نمایش افکت برای Hitهای بسیار نزدیک است.

تنظیم «Remove animations» در بعضی دستگاه‌های Android باعث می‌شود Chrome مقدار `prefers-reduced-motion: reduce` بدهد. قانون عمومی کاهش Motion قبلاً Animationهای Countdown و خرچ/خروچ را مستقیماً به فریم نهایی `opacity: 0` می‌برد. چون رشد نرم این دو افکت بخشی از بازخورد اصلی Gameplay است، فقط Animation اصلی Countdown و خرچ/خروچ با Override هدفمند حتی در این حالت اجرا می‌شود؛ Combo ثابت می‌ماند و سایر Motionهای غیرضروری همچنان کاهش می‌یابند. انتقال سایت از Local به Server این Media Query سمت Client را تغییر نمی‌دهد.

## Pause محدود با ساعت Monotonic

Pause ورودی، حرکت Targetها و تایمر Client را با هم متوقف می‌کند. بودجه‌ی آن در هر بازی مجموعاً ۳۰ ثانیه است تا Session برای کاربر عادی نامحدود نشود و پایان نتیجه همچنان داخل Grace Window سرور انجام شود. برای فاز جایزه‌دار، Pause باید به رویداد سرور تبدیل شود تا سقف آن فقط متکی به Client نباشد.

## Combo امتیازی در یک Gesture

برای جلوگیری از Comboهای تصادفی، فقط Hitهای یک تماس پیوسته که حداکثر ۳۰۰ میلی‌ثانیه از اولین Hit خوشه فاصله دارند شمرده می‌شوند. نمایش از `COMBO 3X` شروع و با Hitهای بعدی همان Gesture به‌روزرسانی می‌شود. Client امتیاز را فوری پیش‌نمایش می‌کند، اما Server پس از اعتبارسنجی Hitهای پایه ضریب را مستقل اعمال می‌کند: سه‌تایی ۱.۵، چهارتایی ۲ و به‌طور عمومی `n/2`.

## Burst قطعی و موزیک کوتاه‌شده

Schedule نسخه‌ی ۷ با Seed سرور گاهی Burstهای ۲ تا ۴ آیتمی می‌سازد تا فرصت Combo واقعاً ایجاد شود و همان الگو سمت سرور قابل بازسازی بماند. برای جلوگیری از ازدحام، پس از Burstهای سه/چهارتایی دو گروه و پس از Burst دوتایی یک گروه فقط تک‌آیتمی تولید می‌شود. موزیک کامل ۲:۱۶ وارد Bundle نشده؛ فقط ۶۱ ثانیه‌ی مورد استفاده با Bitrate برابر 128kbps و Fade ده‌ثانیه‌ای نگهداری می‌شود تا شروع، Pause و پایان روی موبایل سبک‌تر و قابل پیش‌بینی باشد.

## پس‌زمینه و صدای شمارش معکوس سبک

فایل `background.png` برای ارزیابی Creative به WebP شانزده‌کیلوبایتی تبدیل و با `background-size: cover` استفاده شده است. HUD بر پایه‌ی نارنجی `#EE9F35` طراحی شده که کمی تیره‌تر و اشباع‌تر از مرجع `#F2B049` است؛ دامنه‌ی گرادیان محدود و سایه روشن‌تر شده تا سطح اعداد واقعاً نارنجی دیده شود و دورخط تیره خوانایی روی چوب قهوه‌ای را حفظ کند. عدد صفر شروع هیچ Override رنگی ندارد و دقیقاً ظاهر اعداد ۳، ۲ و ۱ را به ارث می‌برد. صدای سه‌ثانیه‌ای شروع به‌جای افزودن فایل سنگین تازه، از نویز فیلترشده و نمونه‌ی Crunch موجود ساخته شده و همزمان با شمارش معکوس پخش می‌شود.

## OTP Preview موقت

نمایش کد فقط برای تست Core Gameplay است. ساختار Challenge/Verify طوری جدا شده که Provider پیامک بعداً بدون تغییر جریان UI اضافه شود.

## محدودیت مرحله‌ای درخواست OTP

برای اصلاح اشتباه ورود کد یا نرسیدن پیام، دو درخواست نخست هر شماره در یک پنجره‌ی ۶۰ ثانیه‌ای آزاد است. درخواست سوم قفل تازه‌ی ۶۰ ثانیه‌ای ایجاد می‌کند. وضعیت در PostgreSQL و با Upsert اتمیک نگهداری می‌شود تا چند Tab یا درخواست همزمان آن را دور نزند؛ UI فقط `retryAfterSeconds` سرور را ثانیه‌به‌ثانیه نمایش می‌دهد.

## بازی قبل از ورود و Claim پس از پایان

برای کاهش اصطکاک، Start و Finish بازی عمومی‌اند و ورود فقط هنگام ثبت نتیجه لازم است. هر GameSession یک Token تصادفی ۲۵۶ بیتی دارد؛ Token خام روی همان Browser و فقط Hash آن در Database نگهداری می‌شود. نتیجه‌ی Finish تا ۲۴ ساعت Claim‌پذیر است و فقط یک User می‌تواند آن را به تاریخچه‌ی خود متصل کند. نگهداری موقت Browser باعث می‌شود شکست OTP یا اینترنت نتیجه را فوراً از بین نبرد.

## ورود و ثبت‌نام جدا

Dialog دو حالت صریح دارد. Login برای شماره‌ی موجود و Register برای شماره‌ی تازه است؛ Register علاوه بر نام، کد معرف اختیاری می‌پذیرد. نام نمایشی Unique نیست و بعداً از پروفایل تغییر می‌کند.

## نقش ادمین و Ban نرم

نقش `ADMIN` در Database نگهداری و تمام APIهای مدیریت با Guard سمت سرور محافظت می‌شوند. نمایش شرطی پنل در Client فقط برای تجربه‌ی کاربری است و جای کنترل دسترسی را نمی‌گیرد. Ban از نوع Soft انتخاب شده تا User، تاریخچه‌ی بازی و شواهد بررسی باقی بمانند؛ همزمان همه‌ی Sessionها باطل، OTP و ورود همان شماره رد و User از لیدربورد حذف می‌شود. برای جلوگیری از قفل‌شدن مدیریت، حساب‌های ادمین از داخل همین پنل قابل Ban نیستند.

ساخت و ارتقای ادمین عمداً API ندارد. ثبت‌نام نقش `USER` را صریح می‌نویسد، Payload دارای `role` در همه‌ی DTOهای مرتبط رد می‌شود و Guard نقش تازه‌ی Database را در هر درخواست می‌بیند. چون OTP Preview عمومی برای حساب ادمین معادل افشای عامل ورود است، Request و Verify ورود ادمین در Production تا اتصال Provider امن مسدود شده‌اند؛ نشست فعلی ادمین بدون تغییر می‌ماند.

فهرست مدیریت به سه Query مستقل `admins`، `users` و `banned` تقسیم شده تا فیلتر قبل از Pagination در سرور اجرا شود. این انتخاب باعث می‌شود تعداد، جست‌وجو و «نمایش بیشتر» هر Tab دقیق باشد؛ User پس از Ban یا Unban از Tab فعلی خارج و در گروه درست دیده می‌شود.

## امتیاز دعوت و لیدربورد

هر کاربر یک کد ده‌کاراکتری یکتا دارد و رابط خود کد را برای اشتراک کپی می‌کند. ثبت‌نام با کد فقط رابطه‌ی معرف را ثبت می‌کند؛ اولین Claim با امتیاز بیشتر از صفر، ۱٬۰۰۰ امتیاز به معرف فعال می‌دهد و یک `ReferralReward` یکتا برای Audit می‌سازد. این شرط ثبت‌نام‌های بدون بازی را بی‌اثر می‌کند. High Score بازی معیار لیدربورد باقی مانده و امتیاز دعوت در `totalScore` پروفایل دیده می‌شود. لیدربورد با Offset در صفحه‌های ده‌تایی خوانده می‌شود و رتبه‌ی User فعلی جداگانه برمی‌گردد.

## WebMCP محدود و Read-only

فقط خواندن ده رکورد برتر به‌عنوان ابزار ساختاریافته ارائه می‌شود. شروع خودکار بازی از طریق Agent اضافه نشده، چون آغاز یک Session یک‌دقیقه‌ای بدون حضور بازیکن باعث مصرف تلاش و تجربه‌ی ناقص می‌شود.
