# امنیت و کنترل تقلب

## کنترل‌های نسخه‌ی فعلی

منبع حقیقت Score سرور است. Client فقط اطلاعات هر Hit را گزارش می‌کند و سرور با Seed ذخیره‌شده Schedule را بازسازی می‌کند. موارد ناشناخته، تکراری، خارج از Window حضور Target، Swipe بسیار کوتاه/طولانی و Burst غیرممکن پذیرفته نمی‌شوند.

شروع و پایان از ساعت سرور استفاده می‌کنند. پایان عادی قبل از پایان ۶۰ ثانیه یا بیش از ۹۰ ثانیه پس از پایان پذیرفته نمی‌شود. پایان دستی زودهنگام فقط با فلگ صریح مجاز است و Hitهایی که زمان آن‌ها از زمان واقعاً سپری‌شده‌ی سرور جلوتر باشد رد می‌شوند. هر User فقط یک Session فعال دارد و Rate Limit اولیه‌ی شروع بازی روی Database اعمال می‌شود.

Pause ساعت Monotonic و Gameplay مرورگر را واقعاً متوقف می‌کند، اما بودجه‌ی تجمعی آن در UI حداکثر ۳۰ ثانیه است و در Grace Window ثبت نتیجه جا می‌گیرد. این سقف در فاز فعلی Client-side است؛ دست‌کاری آن Target یا Score تازه ایجاد نمی‌کند، چون Schedule معتبر همچنان فقط ۶۰ ثانیه و امتیاز سمت سرور محاسبه می‌شود. برای مسابقه‌ی جایزه‌دار، ثبت بازه‌های Pause در سرور پیشنهاد می‌شود.

Client فقط `gestureId` و Hit telemetry را گزارش می‌کند و Score یا ضریب قابل اعتماد ارسال نمی‌کند. سرور ابتدا Target، زمان حضور و ویژگی‌های Swipe را اعتبارسنجی می‌کند؛ سپس فقط برای Hitهای معتبر با Gesture یکسان و فاصله‌ی حداکثر ۳۰۰ میلی‌ثانیه از ابتدای خوشه، ضریب Combo را اعمال می‌کند. جعل `gestureId` به‌تنهایی Target یا Hit تازه‌ای تولید نمی‌کند، هرچند تحلیل رفتار Pointer سمت سرور همچنان پیشنهاد فاز جایزه‌دار است.

Burstهای چندآیتمی و Cooldown پس از گروه‌های بزرگ بخشی از Schedule قطعی نسخه‌ی ۷ هستند و در بازسازی سرور نیز حضور دارند؛ پس افزایش همزمان Targetها مسیر ارسال Hit جعلی تازه‌ای ایجاد نمی‌کند.

OTP با HMAC و Session Token با Hash ذخیره می‌شوند. Cookie در Production باید `Secure` باشد و HTTPS الزامی است.

## محدودیت‌های آگاهانه‌ی MVP

هیچ بازی Browser-based کاملاً ضد Bot نیست. کاربر ماهر می‌تواند API و Schedule را مشاهده کند؛ هدف فعلی جلوگیری از Score جعلی ساده، Replay و دست‌کاری مستقیم عدد امتیاز است.

Rate Limit فعلی per-user و Database-based است. برای چند API instance یا حمله‌ی توزیع‌شده کافی نیست. نمایش OTP نیز فقط برای تست است و نباید با جایزه‌ی واقعی فعال بماند.

## پیشنهاد فاز انتشار

1. اتصال SMS واقعی و Rate Limit بر اساس mobile + IP + device signal؛
2. نگهداری Secretهای Production خارج از Git؛
3. امضای کوتاه‌عمر Chunkهای Schedule یا ارسال مرحله‌ای Targetها؛
4. ثبت telemetry آماری مانند hit ratio، فاصله‌ی زمانی ثابت و الگوی غیرانسانی؛
5. صف بررسی دستی برای Scoreهای برتر و outlierها؛
6. محدودیت تلاش روزانه طبق قوانین کمپین؛
7. Reverse proxy rate limit و WAF؛
8. Audit log برای تغییر وضعیت Score مشکوک؛
9. عدم اعلام برنده به‌صورت خودکار بدون تأیید نهایی.

بهترین نسبت سادگی به اثر برای فاز بعد: SMS واقعی + محدودیت روزانه + بررسی دستی ۲۰ رکورد برتر + Rate Limit لبه‌ی شبکه.
